# Design Decisions

## Repo structure

- Flat single-package repo: the Next.js app lives at the repo root (`src/`, `public/`, `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`, `eslint.config.mjs`) — Next.js requires its config co-located with the app it builds, so there's no separate `frontend/` folder. `backend/` is the only subfolder.
- One root `package.json` for both apps, one root `.env.example`/`.env` (backend-only vars and `NEXT_PUBLIC_*` vars side by side, documented as such), one `tsconfig.json` in the whole repo (Next's).
- `backend/` has no config file of its own. `build:backend`/`typecheck:backend` run `tsc` with compiler options as CLI flags against a file list from `find backend/src -name '*.ts'` (guarded: prints a placeholder instead of erroring while `backend/src/` is empty). `find` instead of a shell glob because POSIX `sh` (what npm scripts run under) doesn't support recursive `**`.
- `next.config.ts` loads the root `.env` via `dotenv` (`quiet: true` — suppresses a benign but noisy self-promotional string the package prints by default; verified against the public npm registry hash, no outbound network code in the package).
- Redis for local dev: native `apt install redis-server`, not Docker. Docker Compose is still the Step 13 production target.
- Execution cadence: one guideline step at a time, pausing for review/testing after each.
- Every file change in this repo is auto-committed and pushed to `github.com/sadekur/flowSync` by a tool outside this session (not something run here) — confirmed intentional by the user.

## Security & architecture principles (enforced as each piece is built)

- **Auth tokens**: JWT access (~15m) + refresh (~7d), both `httpOnly` + `Secure` + `SameSite=Strict` cookies set by the backend — never in a JSON response body, never in `localStorage`/Redux. Redux only ever holds the decoded user profile, never a raw token.
- **CSRF**: cookie-based auth needs a second layer beyond `SameSite=Strict` — state-changing REST routes require a custom header (`X-CSRF-Token` double-submit, or `X-Requested-With`) that a cross-site form/script can't attach.
- **Clickjacking/CSP**: `frame-ancestors 'none'` + `X-Frame-Options: DENY`, strict `Content-Security-Policy` (`default-src 'self'`, no `unsafe-inline`/`unsafe-eval`, nonce for any unavoidable inline script), `X-Content-Type-Options: nosniff`, restrictive `Permissions-Policy` — set in Next.js middleware, repeated at Nginx in prod (Step 13) as defense in depth.
- **CORS**: backend allowlists exactly the frontend origin, `credentials: true`, no wildcard.
- **Secrets**: only ever in backend `.env` reads; the frontend build only consumes `NEXT_PUBLIC_*` values. No secret-shaped value is allowed into a `NEXT_PUBLIC_*` var.
- **File storage** (post-MVP feature, principle fixed now): bucket stays private, never reachable directly by the client. All upload/download traffic goes through the backend, which proxies the bytes or issues short-lived scoped pre-signed URLs. Bucket credentials are backend-only secrets.
- **Caching**: Redis cache-aside on hot read endpoints with explicit invalidation on writes; presence lives only in Redis (never Mongo); Next.js server-component `fetch` calls set explicit `cache`/`revalidate` per route rather than relying on defaults.
- **State management**: Redux Toolkit owns auth/UI/real-time-synced entities; `createEntityAdapter` normalizes tasks/messages/notifications by id; a single `socketMiddleware` is the only thing that touches the Socket.IO client, translating server events into dispatched actions.
- **Server/Client components**: route segments are Server Components fetching with the forwarded httpOnly cookie; a thin `StoreHydrator` client boundary seeds Redux from server-fetched props; everything interactive is a Client Component; list-item presentational components (`TaskCard`, `MessageBubble`, etc.) are `React.memo`-wrapped to keep socket-driven updates from cascading into full-list re-renders.

## Step 2 — Backend bootstrap

- **Express 5**, not 4 — current npm-resolved default, and its native handling of rejected promises in route handlers is a nice bonus. `asyncHandler` is still used explicitly for clarity rather than relying on that.
- **Env loading**: `backend/src/config/env.ts` loads the root `.env` via `dotenv` (mirrors `next.config.ts`) and validates it through a `zod` schema, failing fast with a clear per-field message and `process.exit(1)` if anything required is missing/malformed — rather than surfacing a confusing error deep inside a request handler later.
- **Redis client**: `ioredis`, with `lazyConnect: true` — connects explicitly in `server.ts` so startup fails fast (and loudly) if Redis is unreachable, instead of the app silently coming up "half-working."
- **`http.createServer(app)`** in `server.ts` instead of `app.listen()` directly — no behavior difference yet, but lets Step 6 attach Socket.IO to the same server without touching this file.
- **`GET /api/health`**: checks live `mongoose.connection.readyState` and a real Redis `PING`, returns `200`/`ok` or `503`/`degraded` — verified both paths live: fails fast with a clear error when Redis is down, and returns `200 ok` with both services connected once Redis was installed.

## Step 3 — Authentication

- **Password hashing**: `bcryptjs` (pure JS, not native `bcrypt`) — no native build step needed, one less thing to break across environments; cost factor 12. `passwordHash` has `select: false` on the schema so a stray `User.find()` never leaks it — login explicitly `.select("+passwordHash")`s it back.
- **Token rotation**: every successful register/login/refresh reissues *all three* cookies (access, refresh, CSRF) rather than only the expired one — simpler client mental model (one cookie set = one logical session) and avoids a stale CSRF token outliving the refresh token it's meant to protect.
- **`tokenVersion` on `User`**: embedded in the refresh token payload and compared on every refresh. Not used yet (nothing bumps it), but it's the mechanism for a future "log out everywhere" / forced-invalidation on password change, without needing a server-side token blocklist.
- **CSRF — double-submit, not a session store**: `csrfToken` is a random value set as a **non-`httpOnly`** cookie; `POST /api/auth/refresh` and `POST /api/auth/logout` require it echoed back in an `X-CSRF-Token` header, checked by a new reusable `middleware/csrf.ts`. `register`/`login` are exempt — pre-session, so there's no cookie yet for a forged request to piggyback on, and the requests aren't acting on an existing account. Every future mutating route (Step 4+) should apply the same middleware rather than reinventing CSRF handling.
- **Logout doesn't revoke tokens server-side**: it only clears the three cookies. A stolen access token would still work for its remaining ~15m regardless of logout — acceptable for the MVP; `tokenVersion` bump is the documented upgrade path if that's ever not acceptable.
- **`errorHandler` gained `ZodError` handling** (400 + per-field `issues` array) — the validators (`validators/auth.validators.ts`) call `schema.parse()` directly in the controller rather than a validation middleware, so the shared error handler is what turns a thrown `ZodError` into a client-usable response.
- **Cookie `maxAge` derived from env, not hardcoded**: `utils/cookies.ts` runs `JWT_ACCESS_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` (already-validated env strings like `"15m"`/`"7d"`) through the `ms` package (already a transitive dep of `jsonwebtoken`; added as a direct dependency since it's now imported directly) so the cookie lifetime always matches the actual JWT lifetime with one source of truth.

## Step 4 — Workspace & Project CRUD

- **Permission model kept deliberately flat**, per PLANNING.md's "complex permissions" out-of-scope note: a workspace has one `owner` (creator) plus a `members` array the owner is always included in. Only the owner can rename/delete the workspace or manage membership; *any* member can create/read/update/delete every project and task inside it — no per-project roles, no "creator can edit, others can't." Simplest thing that lets multiple people collaborate; can be layered on later without a schema migration (roles would just replace the flat `members: ObjectId[]` with `members: { user, role }[]`).
- **Membership middleware over per-controller checks**: `middleware/membership.ts` exports composable pieces (`loadWorkspace` → `requireWorkspaceMember`/`requireWorkspaceOwner` → `loadProject` → `loadTask`) chained directly in the route definitions (see `routes/*.routes.ts`), rather than re-checking membership inside each controller. Keeps the authorization rule visible at the route declaration, not buried in service code.
- **Flat route files, not nested Express routers**: `project.routes.ts`/`task.routes.ts` each declare their full literal path (`/workspaces/:workspaceId/projects/...`) and mount at `/api` directly, same pattern as `auth.routes.ts`, instead of `Router({ mergeParams: true })` sub-mounting. One less layer of indirection for three routers total.
- **Task's `workspace` field is denormalized** from `project.workspace` — set once at task creation from the already-loaded `req.workspace`. Avoids an extra `Project` lookup on every task read/membership check; the tradeoff (an extra field to keep in sync) never actually needs syncing since tasks aren't moved between projects in the MVP.
- **Assignee must already be a workspace member** (checked in `task.service.ts`), enforced at write time rather than via a schema-level constraint — Mongoose can't express "must be in this other document's array" declaratively.
- **Cascading deletes are explicit, not Mongoose middleware hooks** (`workspace.service.ts`/`project.service.ts` delete children before the parent): keeps the deletion order visible in one place instead of hidden in a `pre("deleteOne")` hook on three different models.
- **Frontend (Step 5) deliberately not started alongside this step**: asked and confirmed with the user rather than building a quick login/register UI to exercise Step 3 early — PLANNING.md's order (backend CRUD fully done first) stands.

## Step 5 — Frontend shell

- **Mutations call the Express API directly from Client Components** (`credentials: "include"` + a hand-attached `X-CSRF-Token`, see `lib/client-api.ts`), rather than proxying through Next.js Server Actions. Server Actions would need to manually replicate the browser's role in the double-submit CSRF check (forward the incoming `csrfToken` cookie, relay every `Set-Cookie` from Express back via `cookies().set()`) — extra plumbing for no real gain here, and it would contradict the CSRF rationale already on record ("a cross-site form/script can't attach a custom header" — that defense only means something if the browser itself is the one attaching it). Server Components still do reads with the forwarded cookie, per the original Step 1 principle.
- **Redux store is a per-render factory (`makeStore()`), not a module-level singleton**: Next.js Server Components share one Node process across every user's request, so a singleton `configureStore()` call at module scope would leak state between unrelated users. `StoreProvider` calls `makeStore()` once via `useState`'s lazy initializer, and `StoreHydrator` (a client boundary, per Step 1's convention) seeds the real per-viewer state from the server-fetched `user` prop on mount.
- **`useState(makeStore)` over `useRef` for the store instance**: the more obvious `useRef` + `if (!ref.current)` lazy-init pattern is flagged by the `react-hooks/refs` lint rule (React Compiler-oriented, ships with this Next.js version's `eslint-config-next`) as unsafe ref access during render, even though it's the officially-documented idiom. `useState`'s lazy initializer achieves the same "construct once" result without touching a ref during render.
- **`GET /api/workspaces/:workspaceId` populates `owner`/`members`, no other workspace/project/task route does**: the project page needs member names for the task-assignee dropdown; every authorization check (`middleware/membership.ts`, the services) needs `members` to stay an array of raw ObjectIds to compare against `req.userId`. Populating only in the one read-only, terminal controller keeps both needs satisfied without a shape that authorization code has to special-case.
- **`/projects/[id]` takes the workspace id as a `?workspace=` query param**, not a second path segment — `PLANNING.md` specifies the frontend route as `/projects/[id]` (not `/workspaces/[id]/projects/[id]`), but the backend API is nested under workspace (Step 4). The query param bridges the two without adding a flat `GET /api/projects/:id` backend route that would need its own from-scratch membership check.
- **Slug-based URLs, added after initial user feedback that raw ObjectIds looked wrong in the address bar**: `Workspace`/`Project` each got a `slug` field (`utils/slug.ts`), generated once from `name` at creation and **never regenerated on rename** — a stable URL matters more than a slug tracking the latest name. Workspace slugs are unique globally (workspace routes are top-level); project slugs are unique per-workspace (`{ workspace, slug }` compound index), not globally, since the frontend route already carries the workspace context via `?workspace=`.
- **Route params accept either the ObjectId or the slug, not slug-only** (`middleware/membership.ts`'s `idOrSlugFilter`): every existing internal call site (the dashboard's own data-fetching, `CreateProjectForm`, etc.) kept working unchanged, since the backend doesn't care which form it's given — only the one user-visible `Link href` in `dashboard/page.tsx` was switched to use `.slug`. `Task` has no slug; it's never linked to directly, only shown inline in a project's task list.
- **Backfilling pre-existing data is required whenever a `unique` field is added to a schema with rows already in production-equivalent data** — learned the hard way here: adding `unique: true` on `Workspace.slug` without backfilling left every pre-existing workspace/project without a `slug` field, and MongoDB's background `autoIndex` silently failed to build that index at all (multiple documents missing a field collide as "null" under a standard unique index) — so uniqueness went unenforced with no visible error until checked directly. Fixed with a one-off backfill script (assign slugs to every row missing one, per the same collision-avoidance logic as `generateUniqueSlug`) run before the index was allowed to build. Any future `unique` field added to an existing collection needs the same treatment.
- **Always verify which MongoDB `MONGO_URI` is actually configured before running any ad-hoc query/cleanup script** — learned the hard way here too: `.env`'s `MONGO_URI` points at a remote Atlas cluster (not the local `mongod` from Step 2's original setup), but several earlier "cleanup" commands in this session ran bare `mongosh <db>` with no connection string, silently hitting the *local* database instead — every prior "deleted" test user/workspace from Steps 3–5 was actually still live in Atlas the whole time, undetected until this slug backfill forced a direct inspection. Any future one-off DB script must load `MONGO_URI` from `.env` (e.g. via `dotenv`), never assume a bare `mongosh` invocation is pointed at the right place.
- **No client-side session refresh-on-401 yet**: if the ~15m access token expires mid-session, a Server Component's `/api/auth/me` call simply returns null and the page redirects to `/login`, rather than silently calling `/api/auth/refresh` first. Acceptable for the MVP; revisit if it proves annoying once real usage sessions run longer than 15 minutes.

## Step 6 — Socket.IO wiring

- **Same server, same port as REST**: `createSocketServer(httpServer)` in `backend/src/sockets/index.ts` attaches to the `http.createServer(app)` instance from Step 2. No second port and no second CORS origin to manage. Shutdown now calls `io.close()`, which also closes the HTTP server and drops open sockets. A bare `httpServer.close()` would wait forever on long-lived connections.
- **Auth reuses the REST cookie, parsed by the same `cookie-parser`**: `io.engine.use(cookieParser())` runs the existing Express middleware on handshake requests, and `sockets/auth.ts` verifies `accessToken` exactly like `requireAuth`, storing `socket.data.userId`. No token is sent through `auth: {}` in the handshake payload, because that would require JS-readable tokens, which contradicts the httpOnly-only rule.
- **Explicit Origin check (`allowRequest`) on top of Socket.IO's `cors` option**: `cors` only covers the HTTP long-polling transport. Browsers don't apply CORS to WebSocket upgrades, so without the check any page could open an authenticated WebSocket using the victim's cookies (cross-site WebSocket hijacking). `SameSite=Strict` already blocks most of this, but "same-site" includes other ports and subdomains, so the exact-Origin check is the real guard. Verified live that a foreign or missing Origin is rejected on both transports.
- **Auth is per-handshake, not per-event**: once connected, a socket stays authenticated past the ~15m access-token expiry until it disconnects. Every reconnect re-verifies. This is acceptable for the MVP and consistent with Step 3's note that logout doesn't revoke tokens server-side. The upgrade path, if needed, is a timer that disconnects at the token's `exp`.
- **Room membership is checked only at join time**: a user removed from a workspace stays in its project rooms until they leave or reconnect. The fix, if it matters, is `io.in(projectRoom(id)).socketsLeave` for that user's sockets inside `removeMember`, once Step 9/10 give the REST layer access to `io`.
- **Rooms are keyed by canonical ObjectId, never slug** (`project:{_id}`). `project:join` rejects slugs, so one project can't end up as two rooms depending on how the page was linked. The project page passes `project._id` (not the URL slug) to the client.
- **Join answers "not found" for both missing and not-a-member**, mirroring how the REST layer avoids confirming existence to non-members.
- **Acks instead of fire-and-forget emits** for join/leave, so the client knows whether it's actually in the room. The UI's "Live" badge is driven by the ack (`joinedProjectId`), not by the connection alone.
- **`socketMiddleware` is the only Socket.IO client code, created per store**: `createSocketMiddleware()` is called inside `makeStore()`, so it follows the same no-module-singleton rule as the store. The socket is created lazily on the first `socketConnect` action, which is only dispatched from client effects, so nothing socket-related runs during server rendering. Components dispatch plain commands (`socketConnect`, `joinProject`, …) and read `state.socket`.
- **Connection lifecycle follows auth**: `StoreHydrator` dispatches `socketConnect` when it hydrates a signed-in user (and `socketDisconnect` for `null`), and `LogoutButton` disconnects explicitly. Pages don't manage connections individually.
- **Automatic room re-join after reconnect**: server-side rooms are per-connection, so the middleware remembers the project the UI wants (`activeProjectId`, separate from the acked `joinedProjectId`) and re-emits `project:join` on every `connect`. If a join ack arrives after the page has already moved on (quick navigation, or React Strict Mode's mount/unmount/mount), the middleware immediately emits `project:leave` so no stale room lingers.
- **Event types are hand-mirrored** between `backend/src/sockets/types.ts` and `src/types/socket.ts`: the frontend's tsconfig excludes `backend/`, and a shared package would break the one-package/one-tsconfig repo rule. There are only a few event types, so keeping two copies in sync is cheap.

## Step 7 — Real-time chat

- **Send over the socket, read over REST**: `message:send` is a socket event because the sender is already connected and the ack gives immediate success/failure. History (`GET …/messages`) is REST so the project page's Server Component can fetch the first page with the forwarded cookie, like tasks. There's no REST send route, so there's only one write path to secure, and CSRF doesn't apply to it: the socket has no cross-site form equivalent, and the exact-Origin check covers hijacking.
- **Membership re-checked on every send**, not trusted from the room. Step 6 accepted that a removed member stays in rooms until reconnect, because receiving is read-only and short-lived. Writing is permanent, so `message:send` runs the same `findProjectForMember` check (`sockets/membership.ts`, now shared with `project:join`) each time. That's two indexed lookups per message, which is fine at chat rates. The sender also doesn't need to be in the room, so a send never fails on a join-ack race.
- **Rate limit in Redis, not in memory**: `utils/rateLimit.ts` is a fixed-window `INCR` + `EXPIRE … NX` in a single `MULTI`, keyed per user (20 per 10 s across all of their tabs). Redis keeps the limit correct once there are several backend instances (Step 11). `NX` plus the transaction means a crash between the two commands can't leave a key without a TTL. `EXPIRE NX` needs Redis ≥ 7.0; Memurai 4.x and `redis:7` both support it. Only payloads that pass validation count, so a malformed spam payload is rejected before it touches Redis.
- **`maxHttpBufferSize` lowered from 1 MB to 64 KB**: the largest legitimate packet is one message (2000 chars, at most ~8 KB of UTF-8). This limits how much a client can make the server buffer per packet.
- **One explicit wire shape (`MessageDto`)** for both the REST response and the broadcast, built field by field in `message.service.ts`. The sender is populated with `name` only. Returning a Mongoose doc through `toJSON` would risk leaking more user fields to everyone in the room.
- **Paging by `_id`, not `createdAt`**: ObjectIds are unique and time-ordered, so one `{ project: 1, _id: -1 }` index serves both cursors with no tie-breaker needed. The client entity adapter sorts by the same `_id` string compare, so server and client always agree on order.
- **`before` and `after` cursors, and a catch-up on every (re)join**: Socket.IO doesn't replay missed events. After each successful `project:join` ack (including the first, which covers the gap between server render and join), `ChatPanel` fetches `?after=<newest id>` and upserts the result. This reuses the Step 6 auto-rejoin, so a dropped connection doesn't leave a silent hole in the chat. It's capped at 5 × 50 messages; beyond that a reload catches up.
- **Dedupe by `_id` instead of optimistic temp messages**: the sender sees their message from the ack and also receives the `message:new` broadcast, and both upsert the same entity. There are no client-side temporary ids to reconcile, and the input keeps its draft until the server confirms, so a failed send never loses text.
- **The dispatch return value carries the ack result**: `socketMiddleware` declares a `SocketDispatchExt`, so `await dispatch(sendMessage(...))` resolves to `{ ok } | { ok: false, error }`. That keeps the "only the middleware touches the socket" rule without putting callbacks or promises into actions, which the serializability check would flag. The middleware is `prepend`ed rather than `concat`ed. Runtime order doesn't matter to it, but only the first dispatch extension's overload wins in the inferred `AppDispatch` type. The hooks moved to react-redux's `.withTypes<>()` form (adding `useAppStore`) so that typed dispatch reaches components.
- **The messages slice holds one project at a time** (the open page). `messagesHydrated` merges when it's the same project, so a `router.refresh()` after a task change doesn't drop live or older messages, and replaces when the project changes. Events for any other project are ignored. The slice resets on `socketDisconnect` (logout), like the socket slice.
- **Plain text only**: messages render as React text nodes (escaped) with `whitespace-pre-wrap`. There's no markdown or HTML rendering, so there's no sanitizer to maintain. HTML is stored verbatim and shown literally (verified with a `<script>` payload).
