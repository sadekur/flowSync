# Design Decisions

## Step 1 — Project Setup

- **Monorepo layout**: `frontend/` (Next.js App Router) + `backend/` (Express) as plain source folders, no `frontend/`/`backend/` `package.json` — a single root `package.json` holds every dependency and all scripts (`dev:frontend`, `dev:backend`, `build:*`, `lint:frontend`, `typecheck:backend`). Chosen over npm workspaces per explicit user preference for exactly one manifest file to maintain, at the cost of slightly less "each app is independently publishable" isolation — irrelevant for an app that's never published as a package.
- **tsconfig stays split, but shares a base**: `frontend/tsconfig.json` and `backend/tsconfig.json` each `extend` a shared root `tsconfig.base.json` (strict mode, `esModuleInterop`, `skipLibCheck`, `noUncheckedIndexedAccess`, etc.). They cannot be fully merged into one file — Next.js requires its own `tsconfig.json` physically inside the directory it builds (`bundler` resolution, DOM lib, JSX) while the backend needs Node-targeted, CommonJS-module `tsc` output (`node` resolution, no DOM lib) — genuinely incompatible compiler options, not just duplication.
- **Single `.env` at repo root**, not one per app. Backend-only secrets (JWT keys, Mongo/Redis URIs, CORS origin) and frontend-only `NEXT_PUBLIC_*` values live side by side in one `.env.example`, documented as such. Backend will read it directly (it runs from the repo root). Next.js does **not** auto-load `.env` files from outside its own project directory, so `frontend/next.config.ts` explicitly loads the root `.env` via `dotenv` (`loadEnv({ path: path.resolve(__dirname, "../.env") })`) before the config is evaluated — this runs early enough that `NEXT_PUBLIC_*` values are still correctly inlined at build time.
  - Tried `node --env-file-if-exists=../.env` on the `next` CLI first (no extra dependency needed) — rejected because Next's Turbopack build spawns worker threads via `NODE_OPTIONS`, and Node explicitly disallows `--env-file` inside `NODE_OPTIONS` (`ERR_WORKER_INVALID_EXEC_ARGV`), so builds hard-failed. The `dotenv`-in-`next.config.ts` approach avoids CLI flags entirely and has no such restriction.
- **`lint:frontend` runs as `cd frontend && eslint .`**, not `eslint frontend` from the root. ESLint's flat config (v9) resolves `eslint.config.mjs` and its `globalIgnores` patterns relative to the current working directory, not per-file nearest-ancestor like the old `.eslintrc` cascade — running from root caused it to miss `frontend/.next/**` in its ignore patterns and lint Next's generated type-checking trampoline files (thousands of false-positive `no-explicit-any` errors). `cd`-ing into `frontend` first makes ignore-pattern resolution match Next's own default `next lint` behavior.
- **Redis for local dev**: native `apt install redis-server`, not Docker — confirmed with the user. Docker Compose is still the target for Step 13 production deployment.
- **How far "single file" goes**: pushed to relocate every frontend config file (`next.config.ts`, `eslint.config.mjs`, `postcss.config.mjs`, `tsconfig.json`, `AGENTS.md`, `CLAUDE.md`) to the repo root, including `src/`/`public/`. Reverted — Next.js requires `next.config.ts` and `tsconfig.json` to live in the same directory as the `src/` it builds; moving only the configs to root while leaving `src/`/`public/` in `frontend/` breaks the build (Next looks for `root/src/app`, finds nothing). Landed on: `frontend/` keeps everything Next.js needs co-located (`src/`, `public/`, `next.config.ts`, `eslint.config.mjs`, `postcss.config.mjs`, `tsconfig.json`, and `AGENTS.md` — which `next dev` itself regenerates in whatever directory holds `next.config.ts`, so it has to stay there too or a stale duplicate reappears at root on every dev/build). `CLAUDE.md` stays at root as the one Claude-Code entry point (that's where the harness looks for it) and imports `@frontend/AGENTS.md` instead of a root copy. `backend/tsconfig.json` similarly can't disappear into a single root file — `tsc` needs it to know backend's Node/CommonJS compiler options and `rootDir`/`outDir`, which are fundamentally incompatible with Next's browser/bundler options; both already minimize duplication by `extend`-ing the single shared `tsconfig.base.json`, which *is* the "one combined file" for compiler options — only the tiny per-app stub (target/module/paths/include) stays local, because each tool hard-requires a config file to exist in its own directory.
- **`eslint.config.mjs` and `AGENTS.md` moved to root** (after the above): `eslint.config.mjs` moving out of `frontend/` is safe once two things are fixed — its `globalIgnores` patterns are resolved relative to *the config file's own location*, so `.next/**` etc. had to become `frontend/.next/**`; and `eslint-config-next`'s Next-app auto-detection (`no-html-link-for-pages` and friends) resolves relative to `process.cwd()`, which is now the repo root, not `frontend/` — fixed with an explicit `settings: { next: { rootDir: "frontend" } }` block. `lint:frontend` runs as `eslint frontend` from the root (no more `cd frontend &&`). Verified both that a real violation is still caught and that the build's ignore patterns correctly skip `frontend/.next/**`.
  `AGENTS.md` is different: read `node_modules/next/dist/server/lib/generate-agent-files.js` directly rather than guessing — `next dev` (only `dev`, confirmed `next build` never calls this) unconditionally ensures `AGENTS.md` or `CLAUDE.md` exists *inside its own project directory* (`frontend/`, wherever `next.config.ts` lives) every time it starts; if neither is present there, it scaffolds both fresh. So moving `AGENTS.md` to root doesn't stop Next from recreating a local `frontend/AGENTS.md` + `frontend/CLAUDE.md` pair the next time anyone runs `npm run dev:frontend` — that's Next's own hardcoded behavior, not something addressable via file placement. Compromise: moved it to root as asked, and added `frontend/AGENTS.md`/`frontend/CLAUDE.md` to `.gitignore` so if `next dev` re-scaffolds them locally they stay untracked disposable duplicates rather than polluting the repo — the root copy stays the one real, committed file.
- **`dotenv`'s console noise**: `next build` printed `injected env (0) from ../.env // tip: ⌁ auth for agents [www.vestauth.com]` — investigated as a possible supply-chain/prompt-injection concern before dismissing it. Confirmed benign: `www.vestauth.com` is a hardcoded string in a `TIPS` array shipped in the officially published `dotenv@17.4.2` (`node_modules/dotenv/lib/main.js`), alongside ads for the maintainer's own `dotenvx.com`; the installed file's hash matches the public npm registry exactly (not locally tampered), and the package has no outbound network/`fetch`/`https.request` code anywhere — it only prints the string, never calls it. Just maintainer self-promotion in console output, not malicious. Silenced with `quiet: true` on the `dotenv.config()` call in `frontend/next.config.ts` rather than left printing unvetted third-party URLs on every build.
- **Final layout — supersedes the "`frontend/` keeps everything" call in the entry above**: pushed further, repeatedly and explicitly, to have zero config files nested in either app folder. Landed here: **no `frontend/` folder at all** — `src/`, `public/`, `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`, `eslint.config.mjs` all moved to the repo root, since Next.js requires its config co-located with the app it builds and there's no CLI flag or config option to separate them (checked `next build --help`/`next dev --help` directly — no such flag exists). `tsconfig.base.json` was folded directly into the now-root `tsconfig.json` and deleted — literally one `tsconfig.json` in the whole repo. **`backend/tsconfig.json` was deleted too**, not just relocated: `build:backend`/`typecheck:backend` now run `tsc` with every compiler option passed as a CLI flag against a file list from `find backend/src -name '*.ts'` (guarded — prints a placeholder message instead of erroring when the list is empty, which it still is pre-Step-2). `find` was chosen over shell globbing (`backend/src/**/*.ts`) specifically because recursive `**` isn't reliable across shells (bash needs `globstar` enabled, POSIX `sh` — what npm scripts actually run under — doesn't support it at all), and this repo's `backend/src/` has real subfolders (`config/`, `models/`, `routes/`, etc.) that a non-recursive glob would silently miss; verified live with a throwaway nested `backend/src/config/env.ts` + `backend/src/utils/logger.ts` + `backend/src/server.ts` importing each other — both `typecheck:backend` and `build:backend` (correct nested `backend/dist/config/`, `backend/dist/utils/` output) worked before the throwaway files were removed. Trade-off accepted knowingly: editing a `backend/*.ts` file in an editor now has no project-local `tsconfig.json` to anchor on (TS language servers will either treat it as an orphan file or, if one climbs the tree, incorrectly pick up the root Next.js config's DOM-lib/bundler settings) — acceptable since there's no backend source yet; revisit if editor intellisense on backend files becomes a real problem once Step 2 adds substantial code.
  `eslint.config.mjs`'s ignores and `AGENTS.md`'s regeneration concerns (previous entry) are now moot in the flattened layout — `.next/**` etc. are correctly root-relative again since the app IS the root, and `next dev` regenerating `AGENTS.md`/`CLAUDE.md` "in its own project directory" now means the root, i.e. exactly where they already live — no more local-duplicate risk, `frontend/AGENTS.md`/`frontend/CLAUDE.md` gitignore entries removed as dead patterns.
  One root `.next/` build-output run was committed to git history before `.gitignore` was updated for the flattened path (it still had `frontend/.next/`, not `.next/`) — caught via `git status` showing ~190 tracked files under `.next/`, fixed by updating `.gitignore` and deleting the directory; the auto-commit tooling (see below) picked up the deletion.
- **Execution cadence**: one guideline step at a time, pausing for review/testing after each — confirmed with the user, overriding the default "ship the whole MVP autonomously" instinct.
- **Auto-commit/push**: every file change in this repo is being committed and pushed to `github.com/sadekur/flowSync` automatically by something outside this session (not `git` commands run here) — confirmed with the user as an intentional tool they have set up (likely a VS Code extension), not something to investigate or disable.

## Security & architecture principles (recorded now, enforced as each piece is built)

- **Auth tokens**: JWT access (~15m) + refresh (~7d), both `httpOnly` + `Secure` + `SameSite=Strict` cookies set by the backend — never in a JSON response body, never in `localStorage`/Redux. Redux only ever holds the decoded user profile, never a raw token.
- **CSRF**: cookie-based auth needs a second layer beyond `SameSite=Strict` — state-changing REST routes will require a custom header (`X-CSRF-Token` double-submit, or `X-Requested-With`) that a cross-site form/script can't attach.
- **Clickjacking/CSP**: `frame-ancestors 'none'` + `X-Frame-Options: DENY`, strict `Content-Security-Policy` (`default-src 'self'`, no `unsafe-inline`/`unsafe-eval`, nonce for any unavoidable inline script), `X-Content-Type-Options: nosniff`, restrictive `Permissions-Policy` — set in Next.js middleware, repeated at Nginx in prod (Step 13) as defense in depth.
- **CORS**: backend allowlists exactly the frontend origin, `credentials: true`, no wildcard.
- **Secrets**: only ever in backend `.env` reads; the frontend build only consumes `NEXT_PUBLIC_*` values. No secret-shaped value is allowed into a `NEXT_PUBLIC_*` var.
- **File storage (post-MVP feature, principle fixed now)**: bucket stays private, never reachable directly by the client. All upload/download traffic goes through the backend, which proxies the bytes or issues short-lived scoped pre-signed URLs. Bucket credentials are backend-only secrets.
- **Caching**: Redis cache-aside on hot read endpoints with explicit invalidation on writes; presence lives only in Redis (never Mongo); Next.js server-component `fetch` calls set explicit `cache`/`revalidate` per route rather than relying on defaults.
- **State management**: Redux Toolkit owns auth/UI/real-time-synced entities; `createEntityAdapter` normalizes tasks/messages/notifications by id; a single `socketMiddleware` is the only thing that touches the Socket.IO client, translating server events into dispatched actions.
- **Server/Client components**: route segments are Server Components fetching with the forwarded httpOnly cookie; a thin `StoreHydrator` client boundary seeds Redux from server-fetched props; everything interactive is a Client Component; list-item presentational components (`TaskCard`, `MessageBubble`, etc.) are `React.memo`-wrapped to keep socket-driven updates from cascading into full-list re-renders.

Full step-by-step build plan lives in `PLANNING.md`.
