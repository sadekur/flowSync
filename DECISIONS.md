# Design Decisions

## Repo structure

- Flat single-package repo: the Next.js app lives at the repo root (`src/`, `public/`, `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`, `eslint.config.mjs`) — Next.js requires its config co-located with the app it builds, so there's no separate `frontend/` folder. `backend/` is the only subfolder.
- One root `package.json` for both apps, one root `.env.example`/`.env` (backend-only vars and `NEXT_PUBLIC_*` vars side by side, documented as such), one `tsconfig.json` in the whole repo (Next's).
- `backend/` has no config file of its own. `build:backend`/`typecheck:backend` run `tsc` with compiler options as CLI flags against a file list from `find backend/src -name '*.ts'` (guarded: prints a placeholder instead of erroring while `backend/src/` is empty). `find` instead of a shell glob because POSIX `sh` (what npm scripts run under) doesn't support recursive `**`.
- `next.config.ts` loads the root `.env` via `dotenv` (`quiet: true` — suppresses a benign but noisy self-promotional string the package prints by default; verified against the public npm registry hash, no outbound network code in the package).
- Redis for local dev: native `apt install redis-server`, not Docker. Docker Compose is still the Step 13 production target.
- Execution cadence: one guideline step at a time, pausing for review/testing after each.
- Every file change in this repo is auto-committed and pushed to `github.com/sadekur/flowSync` by a tool outside this session (not something run here) — confirmed intentional by the user.

## Security & architecture principles (enforced as each piece is built)

- **Auth tokens**: JWT access (~15m) + refresh (~7d), both `httpOnly` + `Secure` + `SameSite=Strict` cookies set by the backend — never in a JSON response body, never in `localStorage`/Redux. Redux only ever holds the decoded user profile, never a raw token.
- **CSRF**: cookie-based auth needs a second layer beyond `SameSite=Strict` — state-changing REST routes require a custom header (`X-CSRF-Token` double-submit, or `X-Requested-With`) that a cross-site form/script can't attach.
- **Clickjacking/CSP**: `frame-ancestors 'none'` + `X-Frame-Options: DENY`, strict `Content-Security-Policy` (`default-src 'self'`, no `unsafe-inline`/`unsafe-eval`, nonce for any unavoidable inline script), `X-Content-Type-Options: nosniff`, restrictive `Permissions-Policy` — set in Next.js middleware, repeated at Nginx in prod (Step 13) as defense in depth.
- **CORS**: backend allowlists exactly the frontend origin, `credentials: true`, no wildcard.
- **Secrets**: only ever in backend `.env` reads; the frontend build only consumes `NEXT_PUBLIC_*` values. No secret-shaped value is allowed into a `NEXT_PUBLIC_*` var.
- **File storage** (post-MVP feature, principle fixed now): bucket stays private, never reachable directly by the client. All upload/download traffic goes through the backend, which proxies the bytes or issues short-lived scoped pre-signed URLs. Bucket credentials are backend-only secrets.
- **Caching**: Redis cache-aside on hot read endpoints with explicit invalidation on writes; presence lives only in Redis (never Mongo); Next.js server-component `fetch` calls set explicit `cache`/`revalidate` per route rather than relying on defaults.
- **State management**: Redux Toolkit owns auth/UI/real-time-synced entities; `createEntityAdapter` normalizes tasks/messages/notifications by id; a single `socketMiddleware` is the only thing that touches the Socket.IO client, translating server events into dispatched actions.
- **Server/Client components**: route segments are Server Components fetching with the forwarded httpOnly cookie; a thin `StoreHydrator` client boundary seeds Redux from server-fetched props; everything interactive is a Client Component; list-item presentational components (`TaskCard`, `MessageBubble`, etc.) are `React.memo`-wrapped to keep socket-driven updates from cascading into full-list re-renders.

## Step 2 — Backend bootstrap

- **Express 5**, not 4 — current npm-resolved default, and its native handling of rejected promises in route handlers is a nice bonus. `asyncHandler` is still used explicitly for clarity rather than relying on that.
- **Env loading**: `backend/src/config/env.ts` loads the root `.env` via `dotenv` (mirrors `next.config.ts`) and validates it through a `zod` schema, failing fast with a clear per-field message and `process.exit(1)` if anything required is missing/malformed — rather than surfacing a confusing error deep inside a request handler later.
- **Redis client**: `ioredis`, with `lazyConnect: true` — connects explicitly in `server.ts` so startup fails fast (and loudly) if Redis is unreachable, instead of the app silently coming up "half-working."
- **`http.createServer(app)`** in `server.ts` instead of `app.listen()` directly — no behavior difference yet, but lets Step 6 attach Socket.IO to the same server without touching this file.
- **`GET /api/health`**: checks live `mongoose.connection.readyState` and a real Redis `PING`, returns `200`/`ok` or `503`/`degraded` — verified both paths live: fails fast with a clear error when Redis is down, and returns `200 ok` with both services connected once Redis was installed.

## Step 3 — Authentication

- **Password hashing**: `bcryptjs` (pure JS, not native `bcrypt`) — no native build step needed, one less thing to break across environments; cost factor 12. `passwordHash` has `select: false` on the schema so a stray `User.find()` never leaks it — login explicitly `.select("+passwordHash")`s it back.
- **Token rotation**: every successful register/login/refresh reissues *all three* cookies (access, refresh, CSRF) rather than only the expired one — simpler client mental model (one cookie set = one logical session) and avoids a stale CSRF token outliving the refresh token it's meant to protect.
- **`tokenVersion` on `User`**: embedded in the refresh token payload and compared on every refresh. Not used yet (nothing bumps it), but it's the mechanism for a future "log out everywhere" / forced-invalidation on password change, without needing a server-side token blocklist.
- **CSRF — double-submit, not a session store**: `csrfToken` is a random value set as a **non-`httpOnly`** cookie; `POST /api/auth/refresh` and `POST /api/auth/logout` require it echoed back in an `X-CSRF-Token` header, checked by a new reusable `middleware/csrf.ts`. `register`/`login` are exempt — pre-session, so there's no cookie yet for a forged request to piggyback on, and the requests aren't acting on an existing account. Every future mutating route (Step 4+) should apply the same middleware rather than reinventing CSRF handling.
- **Logout doesn't revoke tokens server-side**: it only clears the three cookies. A stolen access token would still work for its remaining ~15m regardless of logout — acceptable for the MVP; `tokenVersion` bump is the documented upgrade path if that's ever not acceptable.
- **`errorHandler` gained `ZodError` handling** (400 + per-field `issues` array) — the validators (`validators/auth.validators.ts`) call `schema.parse()` directly in the controller rather than a validation middleware, so the shared error handler is what turns a thrown `ZodError` into a client-usable response.
- **Cookie `maxAge` derived from env, not hardcoded**: `utils/cookies.ts` runs `JWT_ACCESS_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` (already-validated env strings like `"15m"`/`"7d"`) through the `ms` package (already a transitive dep of `jsonwebtoken`; added as a direct dependency since it's now imported directly) so the cookie lifetime always matches the actual JWT lifetime with one source of truth.

## Step 4 — Workspace & Project CRUD

- **Permission model kept deliberately flat**, per PLANNING.md's "complex permissions" out-of-scope note: a workspace has one `owner` (creator) plus a `members` array the owner is always included in. Only the owner can rename/delete the workspace or manage membership; *any* member can create/read/update/delete every project and task inside it — no per-project roles, no "creator can edit, others can't." Simplest thing that lets multiple people collaborate; can be layered on later without a schema migration (roles would just replace the flat `members: ObjectId[]` with `members: { user, role }[]`).
- **Membership middleware over per-controller checks**: `middleware/membership.ts` exports composable pieces (`loadWorkspace` → `requireWorkspaceMember`/`requireWorkspaceOwner` → `loadProject` → `loadTask`) chained directly in the route definitions (see `routes/*.routes.ts`), rather than re-checking membership inside each controller. Keeps the authorization rule visible at the route declaration, not buried in service code.
- **Flat route files, not nested Express routers**: `project.routes.ts`/`task.routes.ts` each declare their full literal path (`/workspaces/:workspaceId/projects/...`) and mount at `/api` directly, same pattern as `auth.routes.ts`, instead of `Router({ mergeParams: true })` sub-mounting. One less layer of indirection for three routers total.
- **Task's `workspace` field is denormalized** from `project.workspace` — set once at task creation from the already-loaded `req.workspace`. Avoids an extra `Project` lookup on every task read/membership check; the tradeoff (an extra field to keep in sync) never actually needs syncing since tasks aren't moved between projects in the MVP.
- **Assignee must already be a workspace member** (checked in `task.service.ts`), enforced at write time rather than via a schema-level constraint — Mongoose can't express "must be in this other document's array" declaratively.
- **Cascading deletes are explicit, not Mongoose middleware hooks** (`workspace.service.ts`/`project.service.ts` delete children before the parent): keeps the deletion order visible in one place instead of hidden in a `pre("deleteOne")` hook on three different models.
- **Frontend (Step 5) deliberately not started alongside this step**: asked and confirmed with the user rather than building a quick login/register UI to exercise Step 3 early — PLANNING.md's order (backend CRUD fully done first) stands.

## Step 5 — Frontend shell

- **Mutations call the Express API directly from Client Components** (`credentials: "include"` + a hand-attached `X-CSRF-Token`, see `lib/client-api.ts`), rather than proxying through Next.js Server Actions. Server Actions would need to manually replicate the browser's role in the double-submit CSRF check (forward the incoming `csrfToken` cookie, relay every `Set-Cookie` from Express back via `cookies().set()`) — extra plumbing for no real gain here, and it would contradict the CSRF rationale already on record ("a cross-site form/script can't attach a custom header" — that defense only means something if the browser itself is the one attaching it). Server Components still do reads with the forwarded cookie, per the original Step 1 principle.
- **Redux store is a per-render factory (`makeStore()`), not a module-level singleton**: Next.js Server Components share one Node process across every user's request, so a singleton `configureStore()` call at module scope would leak state between unrelated users. `StoreProvider` calls `makeStore()` once via `useState`'s lazy initializer, and `StoreHydrator` (a client boundary, per Step 1's convention) seeds the real per-viewer state from the server-fetched `user` prop on mount.
- **`useState(makeStore)` over `useRef` for the store instance**: the more obvious `useRef` + `if (!ref.current)` lazy-init pattern is flagged by the `react-hooks/refs` lint rule (React Compiler-oriented, ships with this Next.js version's `eslint-config-next`) as unsafe ref access during render, even though it's the officially-documented idiom. `useState`'s lazy initializer achieves the same "construct once" result without touching a ref during render.
- **`GET /api/workspaces/:workspaceId` populates `owner`/`members`, no other workspace/project/task route does**: the project page needs member names for the task-assignee dropdown; every authorization check (`middleware/membership.ts`, the services) needs `members` to stay an array of raw ObjectIds to compare against `req.userId`. Populating only in the one read-only, terminal controller keeps both needs satisfied without a shape that authorization code has to special-case.
- **`/projects/[id]` takes the workspace id as a `?workspace=` query param**, not a second path segment — `PLANNING.md` specifies the frontend route as `/projects/[id]` (not `/workspaces/[id]/projects/[id]`), but the backend API is nested under workspace (Step 4). The query param bridges the two without adding a flat `GET /api/projects/:id` backend route that would need its own from-scratch membership check.
- **Slug-based URLs, added after initial user feedback that raw ObjectIds looked wrong in the address bar**: `Workspace`/`Project` each got a `slug` field (`utils/slug.ts`), generated once from `name` at creation and **never regenerated on rename** — a stable URL matters more than a slug tracking the latest name. Workspace slugs are unique globally (workspace routes are top-level); project slugs are unique per-workspace (`{ workspace, slug }` compound index), not globally, since the frontend route already carries the workspace context via `?workspace=`.
- **Route params accept either the ObjectId or the slug, not slug-only** (`middleware/membership.ts`'s `idOrSlugFilter`): every existing internal call site (the dashboard's own data-fetching, `CreateProjectForm`, etc.) kept working unchanged, since the backend doesn't care which form it's given — only the one user-visible `Link href` in `dashboard/page.tsx` was switched to use `.slug`. `Task` has no slug; it's never linked to directly, only shown inline in a project's task list.
- **Backfilling pre-existing data is required whenever a `unique` field is added to a schema with rows already in production-equivalent data** — learned the hard way here: adding `unique: true` on `Workspace.slug` without backfilling left every pre-existing workspace/project without a `slug` field, and MongoDB's background `autoIndex` silently failed to build that index at all (multiple documents missing a field collide as "null" under a standard unique index) — so uniqueness went unenforced with no visible error until checked directly. Fixed with a one-off backfill script (assign slugs to every row missing one, per the same collision-avoidance logic as `generateUniqueSlug`) run before the index was allowed to build. Any future `unique` field added to an existing collection needs the same treatment.
- **Always verify which MongoDB `MONGO_URI` is actually configured before running any ad-hoc query/cleanup script** — learned the hard way here too: `.env`'s `MONGO_URI` points at a remote Atlas cluster (not the local `mongod` from Step 2's original setup), but several earlier "cleanup" commands in this session ran bare `mongosh <db>` with no connection string, silently hitting the *local* database instead — every prior "deleted" test user/workspace from Steps 3–5 was actually still live in Atlas the whole time, undetected until this slug backfill forced a direct inspection. Any future one-off DB script must load `MONGO_URI` from `.env` (e.g. via `dotenv`), never assume a bare `mongosh` invocation is pointed at the right place.
- **No client-side session refresh-on-401 yet**: if the ~15m access token expires mid-session, a Server Component's `/api/auth/me` call simply returns null and the page redirects to `/login`, rather than silently calling `/api/auth/refresh` first. Acceptable for the MVP; revisit if it proves annoying once real usage sessions run longer than 15 minutes.

## Step 6 — Socket.IO wiring

- **Same server, same port as REST**: `createSocketServer(httpServer)` in `backend/src/sockets/index.ts` attaches to the `http.createServer(app)` instance from Step 2. No second port and no second CORS origin to manage. Shutdown now calls `io.close()`, which also closes the HTTP server and drops open sockets. A bare `httpServer.close()` would wait forever on long-lived connections.
- **Auth reuses the REST cookie, parsed by the same `cookie-parser`**: `io.engine.use(cookieParser())` runs the existing Express middleware on handshake requests, and `sockets/auth.ts` verifies `accessToken` exactly like `requireAuth`, storing `socket.data.userId`. No token is sent through `auth: {}` in the handshake payload, because that would require JS-readable tokens, which contradicts the httpOnly-only rule.
- **Explicit Origin check (`allowRequest`) on top of Socket.IO's `cors` option**: `cors` only covers the HTTP long-polling transport. Browsers don't apply CORS to WebSocket upgrades, so without the check any page could open an authenticated WebSocket using the victim's cookies (cross-site WebSocket hijacking). `SameSite=Strict` already blocks most of this, but "same-site" includes other ports and subdomains, so the exact-Origin check is the real guard. Verified live that a foreign or missing Origin is rejected on both transports.
- **Auth is per-handshake, not per-event**: once connected, a socket stays authenticated past the ~15m access-token expiry until it disconnects. Every reconnect re-verifies. This is acceptable for the MVP and consistent with Step 3's note that logout doesn't revoke tokens server-side. The upgrade path, if needed, is a timer that disconnects at the token's `exp`.
- **Room membership is checked only at join time**: a user removed from a workspace stays in its project rooms until they leave or reconnect. The fix, if it matters, is `io.in(projectRoom(id)).socketsLeave` for that user's sockets inside `removeMember`, once Step 9/10 give the REST layer access to `io`.
- **Rooms are keyed by canonical ObjectId, never slug** (`project:{_id}`). `project:join` rejects slugs, so one project can't end up as two rooms depending on how the page was linked. The project page passes `project._id` (not the URL slug) to the client.
- **Join answers "not found" for both missing and not-a-member**, mirroring how the REST layer avoids confirming existence to non-members.
- **Acks instead of fire-and-forget emits** for join/leave, so the client knows whether it's actually in the room. The UI's "Live" badge is driven by the ack (`joinedProjectId`), not by the connection alone.
- **`socketMiddleware` is the only Socket.IO client code, created per store**: `createSocketMiddleware()` is called inside `makeStore()`, so it follows the same no-module-singleton rule as the store. The socket is created lazily on the first `socketConnect` action, which is only dispatched from client effects, so nothing socket-related runs during server rendering. Components dispatch plain commands (`socketConnect`, `joinProject`, …) and read `state.socket`.
- **Connection lifecycle follows auth**: `StoreHydrator` dispatches `socketConnect` when it hydrates a signed-in user (and `socketDisconnect` for `null`), and `LogoutButton` disconnects explicitly. Pages don't manage connections individually.
- **Automatic room re-join after reconnect**: server-side rooms are per-connection, so the middleware remembers the project the UI wants (`activeProjectId`, separate from the acked `joinedProjectId`) and re-emits `project:join` on every `connect`. If a join ack arrives after the page has already moved on (quick navigation, or React Strict Mode's mount/unmount/mount), the middleware immediately emits `project:leave` so no stale room lingers.
- **Event types are hand-mirrored** between `backend/src/sockets/types.ts` and `src/types/socket.ts`: the frontend's tsconfig excludes `backend/`, and a shared package would break the one-package/one-tsconfig repo rule. There are only a few event types, so keeping two copies in sync is cheap.

## Step 7 — Real-time chat

- **Send over the socket, read over REST**: `message:send` is a socket event because the sender is already connected and the ack gives immediate success/failure. History (`GET …/messages`) is REST so the project page's Server Component can fetch the first page with the forwarded cookie, like tasks. There's no REST send route, so there's only one write path to secure, and CSRF doesn't apply to it: the socket has no cross-site form equivalent, and the exact-Origin check covers hijacking.
- **Membership re-checked on every send**, not trusted from the room. Step 6 accepted that a removed member stays in rooms until reconnect, because receiving is read-only and short-lived. Writing is permanent, so `message:send` runs the same `findProjectForMember` check (`sockets/membership.ts`, now shared with `project:join`) each time. That's two indexed lookups per message, which is fine at chat rates. The sender also doesn't need to be in the room, so a send never fails on a join-ack race.
- **Rate limit in Redis, not in memory**: `utils/rateLimit.ts` is a fixed-window `INCR` + `EXPIRE … NX` in a single `MULTI`, keyed per user (20 per 10 s across all of their tabs). Redis keeps the limit correct once there are several backend instances (Step 11). `NX` plus the transaction means a crash between the two commands can't leave a key without a TTL. `EXPIRE NX` needs Redis ≥ 7.0; Memurai 4.x and `redis:7` both support it. Only payloads that pass validation count, so a malformed spam payload is rejected before it touches Redis.
- **`maxHttpBufferSize` lowered from 1 MB to 64 KB**: the largest legitimate packet is one message (2000 chars, at most ~8 KB of UTF-8). This limits how much a client can make the server buffer per packet.
- **One explicit wire shape (`MessageDto`)** for both the REST response and the broadcast, built field by field in `message.service.ts`. The sender is populated with `name` only. Returning a Mongoose doc through `toJSON` would risk leaking more user fields to everyone in the room.
- **Paging by `_id`, not `createdAt`**: ObjectIds are unique and time-ordered, so one `{ project: 1, _id: -1 }` index serves both cursors with no tie-breaker needed. The client entity adapter sorts by the same `_id` string compare, so server and client always agree on order.
- **`before` and `after` cursors, and a catch-up on every (re)join**: Socket.IO doesn't replay missed events. After each successful `project:join` ack (including the first, which covers the gap between server render and join), `ChatPanel` fetches `?after=<newest id>` and upserts the result. This reuses the Step 6 auto-rejoin, so a dropped connection doesn't leave a silent hole in the chat. It's capped at 5 × 50 messages; beyond that a reload catches up.
- **Dedupe by `_id` instead of optimistic temp messages**: the sender sees their message from the ack and also receives the `message:new` broadcast, and both upsert the same entity. There are no client-side temporary ids to reconcile, and the input keeps its draft until the server confirms, so a failed send never loses text.
- **The dispatch return value carries the ack result**: `socketMiddleware` declares a `SocketDispatchExt`, so `await dispatch(sendMessage(...))` resolves to `{ ok } | { ok: false, error }`. That keeps the "only the middleware touches the socket" rule without putting callbacks or promises into actions, which the serializability check would flag. The middleware is `prepend`ed rather than `concat`ed. Runtime order doesn't matter to it, but only the first dispatch extension's overload wins in the inferred `AppDispatch` type. The hooks moved to react-redux's `.withTypes<>()` form (adding `useAppStore`) so that typed dispatch reaches components.
- **The messages slice holds one project at a time** (the open page). `messagesHydrated` merges when it's the same project, so a `router.refresh()` after a task change doesn't drop live or older messages, and replaces when the project changes. Events for any other project are ignored. The slice resets on `socketDisconnect` (logout), like the socket slice.
- **Plain text only**: messages render as React text nodes (escaped) with `whitespace-pre-wrap`. There's no markdown or HTML rendering, so there's no sanitizer to maintain. HTML is stored verbatim and shown literally (verified with a `<script>` payload).

## Step 8 — Typing & presence

- **Presence is a Redis hash per project room, not a set and not Mongo**: `presence:project:{projectId}` maps userId → the number of that user's sockets in the room. The count is what makes multiple tabs behave without a global "is user X connected anywhere" registry: `user:online` broadcasts only on 0 → 1 and `user:offline` only on 1 → 0, so a second tab never makes a user look doubly-online and closing one of two tabs never makes them look offline while the other stays. A hash field per user keeps it to one key per project, deleted fields free memory naturally, and `HKEYS` doubles as the join snapshot.
- **The join ack carries the online snapshot** (`{ ok: true, onlineUserIds }`): presence events aren't replayed, so a page that loads after everyone else joined would otherwise show an empty online list until someone changed. The snapshot is built *after* the joining socket is counted, so it includes the joiner and their own `user:online` broadcast is simply deduped client-side.
- **Presence cleanup rides the `disconnecting` event, not `project:leave` or `disconnect`**: a socket can die (tab crash, network drop, server restart) without ever emitting `project:leave`, and socket.io leaves every room (`join([])`) *before* it emits `disconnect` — checked against the installed 4.8.3 source — so by then `socket.rooms` no longer lists the project rooms. `disconnecting` fires first, while the rooms are still intact, so one pass there removes the socket's presence from each and broadcasts `user:offline` where it was the last one. Presence keys carry a 24 h TTL (refreshed on every change) purely as a crash guard — a backend that dies mid-session can't leave keys forever. Best-effort by design: a missed decrement expires, it can't corrupt anything.
- **`wasPresent` before the decrement, not a Lua script**: HINCRBY alone can't distinguish 1 → 0 (broadcast `user:offline`) from "field never existed" (would return −1). The two-step read-then-decrement is race-benign — concurrent sockets compute the same count, so the worst case is a duplicate `user:offline`, which the idempotent client reducer absorbs. That's simpler to read than an `EVAL` script for zero practical difference.
- **Typing is `to(room)` not `nsp.to(room)`**: unlike `message:new` (where the sender needs the broadcast to dedupe against the ack), the sender's own typing doesn't need echoing back — their input box already knows they're typing. Also ephemeral by design: never stored, never logged, throttled to one `typing:start` per 2.5 s per project client-side, rate-limited (30/10 s) server-side, and peers expire the indicator themselves after ~3.5 s so a crashed tab can't leave "X is typing…" stuck forever.
- **`typing:stop` skips the membership and rate-limit checks**: a stop only ever clears an indicator and reveals nothing — and it fires on input-clear and page navigation, where adding two DB lookups plus a Redis round-trip to a fire-and-forget event buys nothing. `typing:start` keeps the full `findProjectForMember` re-check like `message:send`, so a member removed from the workspace can't leak activity into rooms they joined earlier.
- **Typing throttle lives in the middleware, not the component**: the ChatPanel dispatches `typingStart`/`typingStop` commands on every keystroke; `socketMiddleware` decides when an emit actually goes out (one start per 2.5 s, auto-stop 3 s after the last keystroke, stop emitted on unmount/navigation). Components stay dumb, the "only the middleware touches the socket" rule holds, and the throttle state is per projectId so it survives project switches.
- **Presence display is a slice of the workspace member list, not new data**: the wire format carries raw user ids; the project page already fetches populated `members` for the task-assignee dropdown, so `PresenceList` and the typing indicator just resolve ids against that. No extra REST endpoint, and a removed member who somehow still holds a room slot simply doesn't render.

## Step 9 — Real-time task updates

- **Task writes stay REST; only their delivery is real-time**: unlike chat (`message:send` over the socket), tasks keep the existing REST CRUD because membership + CSRF are already enforced there (`requireWorkspaceMember` / `requireCsrf`) and task writes are low-frequency. The controllers broadcast to `project:{projectId}` after a successful write via `sockets/emitter.ts`. One write path per resource, reusing Step 4's authorization — no socket-side write handler to re-secure.
- **`io` reaches the REST layer through a tiny setter module, not constructor injection**: `io` is created in `server.ts` *after* the Express app (it needs the HTTP server, which needs the app), so controllers can't receive it as a parameter. `sockets/emitter.ts` holds a nullable reference (`setIo(io)` at startup, `setIo(null)` after `io.close()`) and exposes typed `emitTaskCreated/Updated/Deleted` helpers. Null in either window means a stray REST write degrades to "no broadcast" instead of throwing, and it is deliberately the *only* place the REST layer touches `io`.
- **Broadcast includes the actor's own sockets** (`io.to(room)`, not `socket.to(room)`): same rule as chat — the actor sees the change from their REST response immediately, and the broadcast they also receive is deduped by `_id`. One client reducer path handles both.
- **Event payloads are the REST JSON shape**: `task:created`/`task:updated` emit the Mongoose doc (Socket.IO serializes it through the model's `toJSON`, which drops `__v` and stringifies ids/dates), so a task parses identically over HTTP or the socket — the same single-shape goal as `MessageDto`, but without a hand-built DTO since a task has no populated/leaky fields. `task:deleted` sends `{ projectId, taskId }` because the document no longer exists (the ids are captured before `deleteOne`).
- **Three verbs (`created`/`updated`/`deleted`) mirroring the REST methods**, not one `task:changed`: the client's entity adapter has a natural upsert/remove split, and it gives Step 10's notifications meaningful event types to hook.
- **The client keys tasks by canonical `project._id`, not the URL slug**: socket events carry `task.project` (an ObjectId), so `TaskList`/`CreateTaskForm`/`TaskStatusSelect` now get `project._id` (the page previously passed the slug param to the task form). REST accepts either form, so this is a pure alignment with the socket room key (same reasoning as Step 6's "rooms keyed by canonical ObjectId").
- **`tasksSlice` mirrors `messagesSlice`**: one project at a time, `createEntityAdapter` keyed by `_id`, sorted newest-first by **descending `_id`** (matching `GET …/tasks`'s `createdAt: -1` with no date parsing). `tasksHydrated` merges when the project matches and replaces when it changes; the slice resets on `socketDisconnect`. Live `task:*` events *and* a mutation's own REST response both funnel through `taskUpserted`/`taskRemoved`, so the actor updates instantly even if their socket is momentarily down.
- **`router.refresh()` is gone from the task UI**: `CreateTaskForm` and `TaskStatusSelect` dispatch the returned task into the store, and `TaskList` renders from the store (falling back to the server-fetched props until the hydrate effect runs, like `ChatPanel`). The status `<select>` is controlled with a short-lived optimistic value cleared when the PATCH settles, so a change doesn't snap back before the store updates; an effect-based `setState` resync was rejected by the `react-hooks/set-state-in-effect` lint rule (same rule Step 5 hit with the store `ref`), and the optimistic-value pattern avoids it.
- **Catch-up on every (re)join**, same as chat: on `roomJoined`, `TaskList` refetches the full list (it isn't paged) to cover changes between the server render and the join, or during a disconnect. It *merges*, so a live event that races the fetch isn't clobbered; the accepted edge is that a task deleted while disconnected isn't actively removed until a full hydrate (documented in `docs/api/sockets.md`). *Superseded after Step 13: see "Post-MVP fixes".*
- **Cascading project/workspace deletes don't fan out per-task `task:deleted` events**: the project page 404s on the next navigation anyway, so emitting one event per child is write amplification for no live UI. Revisit if a "project deleted while I'm viewing it" live update is ever wanted.
- **This is also the first time the REST layer holds `io`, which Step 6 deferred** (its note: "once Step 9/10 give the REST layer access to `io`"). It unblocks, but does not yet implement, the `socketsLeave`-on-`removeMember` cleanup mentioned there — that's a separate change.

## Step 10 — Real-time notifications

- **Per-user room `user:{userId}`, joined at connection**: notifications are addressed to a person, not a project. Project rooms can't deliver them — a user who isn't viewing the affected project (the whole point of a notification) isn't in that room. So `sockets/index.ts` joins each socket to its own user room at handshake, and `emitNotification` targets `io.to(userRoom(id))`. That reaches every tab the user has open and needs no client-side join (unlike `project:join`). Rooms drop on disconnect automatically, so there's no presence/cleanup to manage.
- **Triggers reuse existing write points; writes stay where they already are**: task notifications are created in `task.controller.ts` (REST), message notifications in `message.handlers.ts` (socket) — the same places those writes already happen. No new write path, no duplicated authorization. One `notification.service.ts` owns persistence + emit so each call site is one line.
- **Assignee-only task scope, never the actor**: a task notification goes to `task.assignee` only, and only when they aren't the actor. This is the GitHub-issues model — far less noise than notifying the whole workspace, and the assignment is the event people actually care about. A changed assignee reads as `task_assigned` (captured from the pre-update `assignee`); an unchanged one as `task_updated`.
- **Message notifications fan out to every workspace member except the sender**: `notifyNewMessage` loads the workspace's `members` (one indexed lookup) and `insertMany`s + emits one row per recipient. This is `members − 1` writes per message — fine at MVP workspace sizes, and the alternative (notify only non-present users via the Step 8 presence hash) was rejected as extra coupling for a step that's already large. Noted as the first thing to revisit if it gets hot.
- **Best-effort, never fails the write it describes**: task notifications are awaited inside a local `try/catch` that only logs; message notifications run *after* the ack with `.catch(log)`. A notification problem must never turn a successful task create / message send into an error, and for messages specifically it must not double-ack.
- **Denormalized `preview` (+ ids), actor populated on read**: `preview` snapshots the task title / first 120 chars of the message, so the list needs no join to the (possibly deleted) source. `actor` is the one populate, exactly like `MessageDto`'s sender, so only `{ _id, name }` can leak. `workspace` + `project` are stored denormalized (like Task/Message) so workspace/project deletes cascade with no lookup.
- **Real unread count, not derived from the page**: `GET /api/notifications` returns the newest 50 plus a `countDocuments({ read: false })`, so the badge is correct even when more than a page of notifications is unread.
- **Mark-all-read on dropdown open**: the simplest read model that keeps a badge meaningful — one `POST /api/notifications/read` (CSRF-protected, since it's state-changing) when the panel opens, then the client clears the badge from the successful response. Per-item toggles were rejected as extra endpoint/UI surface for the MVP.
- **Cascade deletes extended to notifications**: `deleteWorkspace` / `deleteProject` / `deleteTask` now also `Notification.deleteMany` on their key, matching the existing explicit-cascade style rather than Mongo middleware.
- **The bell is a client component in `AppHeader`** (so it's on every authenticated page), seeded by one `GET` on mount and kept live by `notification:new`. It re-fetches per navigation because the header remounts — acceptable, and it means a fresh login always shows the true count.

## Step 11 — Redis at scale

- **Cache what runs per event, not what's slow per page.** The hottest read in the app was `findProjectForMember`: two Mongo queries on every `message:send` and every `typing:start` (up to 30 per user per 10 s). It's now two Redis `GET`s, built from two small cached values: `cache:project:{id}:workspace` (the project's workspace id) and `cache:workspace:{id}:members` (member id list). `notifyNewMessage` reads the same member list, so a chat send now does no membership reads in Mongo when the cache is warm. The third cache is `GET /api/workspaces` per user (`cache:user:{id}:workspaces`), the dashboard's first read.
- **REST loaders (`loadWorkspace`/`loadProject`/`loadTask`) stay on Mongo.** They return full Mongoose documents that controllers then mutate and `save()`. Caching those means rehydrating documents from JSON, and a stale doc could overwrite newer data on save. One indexed lookup per REST request isn't the bottleneck; the per-keystroke socket path was.
- **Socket membership returns a `ProjectRef` (`{ _id, workspace }`), not a `ProjectDocument`.** That's all `createMessage` and `notifyNewMessage` ever used, and it's what makes the check cacheable at all.
- **Invalidate after the write, in the service that does the write.** `workspace.service.ts`, `project.service.ts` and the `utils/cache.ts` helpers own all of it: create (owner's list), rename/add member (member list + every member's list), remove member (same, plus the removed user's list), workspace delete (all of that + every child project's mapping), project delete (its mapping). Delete, don't overwrite: the next read reloads from Mongo, so there's one code path that builds a cached value.
- **Short TTLs as the backstop, sized by what staleness costs.** Delete-after-write has a known race: a reader that loaded the old value just before the write can store it just after the delete. Each key's TTL bounds that. Members get **60 s** because a stale member list is a security issue: a removed user could keep posting until it expires. The project→workspace mapping (only changes on delete) and the dashboard list (cosmetic; clicking through re-checks membership on Mongo) get **5 min**. A failed `DEL` is logged, not thrown, because the Mongo write already succeeded.
- **Fail open to Mongo, never cache "not found".** If Redis errors, `cacheAside` logs and loads from Mongo, the source of truth. A `null` result isn't stored, so a project created a moment after someone probed its id isn't hidden behind a cached miss. Probing with random ids still costs a Mongo lookup, but the per-user socket rate limits already cap that.
- **Plain JSON values with explicit DTOs.** `listWorkspacesForUser` now builds a `WorkspaceSummary` from a `.lean()` read, with exactly the fields `toJSON` used to emit (verified identical key set). That way a cache hit and a miss return byte-identical JSON. Membership is a JSON array checked with `includes`, not a Redis set with `SISMEMBER`: workspaces are small, and one `GET`/`SET EX` pair is simpler than populating a set atomically (`DEL` + `SADD` + `EXPIRE` in a `MULTI`).
- **Redis adapter on its own pub/sub connections.** `@socket.io/redis-adapter` (8.3.0) gets `pubClient`/`subClient`, both `redis.duplicate()`. A subscriber connection can't run normal commands, and keeping publishes off the main client means adapter traffic never queues behind presence, rate-limit or cache commands. All three connect in `connectRedis()` and disconnect in `disconnectRedis()`, so startup still fails fast if Redis is down. The classic (`PUBLISH`) adapter was chosen over the sharded (`SPUBLISH`) one: it works on any Redis 6+/Memurai, and sharding only matters on Redis Cluster.
- **Nothing above the adapter changed.** Handlers already broadcast with `socket.nsp.to(room)` / `io.to(room)` and kept all shared state (presence, rate limits, now the cache) in Redis rather than process memory, which is what makes multiple instances work. The REST layer's `emitter.ts` broadcasts go through the adapter as well, so a task created on instance A reaches a viewer on instance B. No new env var: the adapter reuses `REDIS_URL`.
- **Verified with two real instances, not a mock**: `PORT=4001` and `PORT=4002` side by side against the same Memurai, with clients split across them. Running more instances locally needs only a different `PORT`; `.env` values never override a variable that's already set.

## Step 12 — Testing

- **Vitest, one config, two projects.** Vitest runs TypeScript and TSX without a separate tsconfig or Babel setup, so the repo still has exactly one `tsconfig.json`. `vitest.config.mts` defines a `backend` project (Node) and a `frontend` project (jsdom) under one `npm test`. Jest would have needed `ts-jest` or Babel plus a second module setup for the backend's CommonJS output.
- **Vitest 4.1.12, not 5.** Vitest 5 and jsdom 30+ require Node 22, while `engines` promises Node 20. So the tooling is Vitest 4.1.12 (maintained 4.x) with jsdom 29.1.1. Through Vite 8, the effective floor for running tests is Node 20.19. Moving to Vitest 5 is part of raising `engines` to 22.
- **Backend tests run the real server against real Mongo and Redis, not mocks.** The behaviour that matters most here lives in the seams: CSRF cookies vs headers, membership middleware, cache invalidation read by the socket check, the Redis adapter carrying REST-originated broadcasts. Mocking Mongoose or Redis would test the mocks. `helpers/server.ts` wires the app exactly like `server.ts` (same `createApp`, `createSocketServer`, `setIo`), only on a random port.
- **A throwaway local database, guarded.** Tests wipe their data before each case, so `setup/env.ts` sets every env var explicitly (dotenv never overrides a set variable, so `.env`'s Atlas URI can't leak in). It refuses to run unless Mongo is local with a `_test` database and Redis is local on a non-zero DB. Local `mongod` and Redis were chosen over `mongodb-memory-server`, which downloads a ~100 MB binary on first run, because both already run on the dev machine. Indexes are rebuilt with `syncIndexes()` after the per-file `dropDatabase()` because the unique ones (email, slugs) are under test. Between tests, `deleteMany` keeps them.
- **Backend files run one at a time** (`fileParallelism: false`): they share that database and Redis DB. The whole backend suite is ~16 s, so parallel files with per-worker databases wasn't worth the complexity. Note that Redis pub/sub ignores DB numbers, so a test server and a running dev server exchange adapter messages. That's harmless, because rooms are keyed by ObjectIds that never overlap.
- **Plain `fetch` with a hand-rolled cookie jar instead of supertest.** The API scopes cookies to `COOKIE_DOMAIN=localhost` while the test server listens on `127.0.0.1`, so a domain-aware jar wouldn't send them. A 60-line client that stores `Set-Cookie` and echoes `csrfToken` as `X-CSRF-Token` mirrors exactly what `client-api.ts` does in the browser, and adds no dependency.
- **bcrypt cost 4 under `NODE_ENV=test` only.** bcryptjs is pure JS: ~0.8 s per hash at cost 12, and most tests register three users. Only `backend/tests/setup/env.ts` sets `NODE_ENV=test`; every other environment keeps cost 12. That took the backend suite from ~100 s to ~16 s.
- **Reconnects are tested twice: at the protocol level and through the real store.** A network drop is simulated with `socket.conn.close()` on the server. That closes the transport, which the client treats as "transport close" and retries, unlike `socket.disconnect()`, which it treats as a deliberate kick. The protocol tests use a raw client to pin what the server guarantees: no room after a reconnect, presence count, auth re-check. The store test runs `makeStore()`'s actual `socketMiddleware` against the real server. Only its `io()` call is wrapped, to add the cookie/Origin headers a browser's `withCredentials` would send. It proves the auto re-join really restores live delivery. Store transitions are recorded with `store.subscribe` rather than polled, because a 50 ms reconnect can fall between two polls.
- **A fake socket for frontend tests** (`src/test/fakeSocket.ts`, swapped in with `vi.mock("socket.io-client", …)`). The test plays the server: accepts or refuses the handshake, drops the connection, pushes events, and answers or times out each emit. That covers what's hard to trigger on demand against a real server: a join ack arriving after the user navigated away, a send timeout, the typing throttle and expiry under fake timers. Components get a real `makeStore()` and a mocked `apiFetch`, so they exercise real reducers and middleware.
- **Frontend tests live next to the code (`*.test.tsx`).** Next's `tsconfig.json` includes them, so `tsc -p tsconfig.json` and ESLint cover them for free. Backend tests sit in `backend/tests/` (outside `typecheck:backend`'s `backend/src` file list). The reconnect test imports `@/store`, and `tsc` has no CLI flag for path aliases, so wiring the tests into that script wasn't worth a second config.
- **Proved the tests can fail.** Five deliberate bugs, applied in a scratch copy (this repo auto-commits every change), were each caught by the expected tests. The bugs: no invalidation of a removed member's list, no membership-cache invalidation, the old PATCH schema, no re-join on connect, and presence cleanup on `disconnect` instead of `disconnecting`.
- **Bug found: `createTaskSchema.partial()` kept the `status` default.** In Zod 4, a `.default()` still applies inside `.optional()`, so `PATCH { title }` came back with `status: "todo"` and reset the task. The UI only ever PATCHes `status`, which is why it went unnoticed. `updateTaskSchema` is now built from the bare field definitions. `updateProjectSchema` uses the same `.partial()` pattern but has no defaults, so it's unaffected. Any future `.default()` on a create schema needs the same treatment.

## Step 13 — Deployment

- **Vercel, one project with two Services, at the user's request; Docker Compose kept for self-hosting.** `PLANNING.md` planned Docker Compose + Nginx only, but the user wants a live Vercel URL. Vercel Services deploy the Next.js app (`web`) and the Express + Socket.IO backend (`api`) as one atomic deployment behind one route table. The alternative, the frontend on Vercel and the backend on a VPS, needs a custom domain.
- **Same-origin is what makes the cookies work.** `*.vercel.app` is on the Public Suffix List, so `flowsync.vercel.app` and `flowsync-api.vercel.app` would be different *sites*. The `SameSite=Strict` auth cookies would never be sent from one to the other. One origin, with `/api/*` and `/socket.io/*` rewritten to `api`, keeps every request first-party. The same shape is used behind Nginx, so both deploys behave alike.
- **Dev stays cross-origin; the deploy settings are "unset".** `CORS_ORIGIN` and `COOKIE_DOMAIN` became optional:
  - Unset `CORS_ORIGIN` means `cors({ origin: false })`, so no cross-origin access at all.
  - Unset `COOKIE_DOMAIN` means host-only cookies, so every preview URL gets its own cookies with nothing to configure.
  - The browser uses relative URLs when `NEXT_PUBLIC_API_URL` / `NEXT_PUBLIC_SOCKET_URL` are unset.
  - Server Components can't use a relative URL, so `server-fetch.ts` uses `BACKEND_INTERNAL_URL`. On Vercel that comes from a private `web → api` service binding (deployment-aware, so previews call their own backend); on Compose it's `http://api:4000`.
- **Socket Origin check: `CORS_ORIGIN`, or same-origin.** A fixed allowlist can't name every preview host, so `isAllowedOrigin` also accepts an Origin whose host equals the host the request was sent to (`X-Forwarded-Host` behind a proxy, otherwise `Host`). That is still a CSWSH guard. A browser sets both Origin and Host itself, and page JS can't add headers to a WebSocket upgrade. A cross-origin polling request with a custom `X-Forwarded-Host` would need a CORS preflight, which `origin: false` refuses. So a page on another site can't pass.
- **WebSocket-only client.** Vercel Functions serve WebSockets but not Socket.IO's long-polling, so the client sets `transports: ["websocket"]`. As a side effect, no load balancer needs sticky sessions. A function's max duration (300 s on Hobby) closes sockets periodically. The client's reconnect → auto re-join → `?after=` catch-up path already treats that like any network drop, and Step 12 tests it against a real server.
- **`vercel.ts` exports the `http.Server`; one `createHttpServer()` for every entry.** Vercel owns the listening and needs the `http.Server`, not the Express app, for WebSocket upgrades. Connections open once per instance at module load. Mongoose buffers queries and ioredis queues commands until connected, so early requests wait rather than fail. `server.ts` (dev/Docker), `vercel.ts` and the test harness all call `createHttpServer()`, so the tests exercise the exact wiring that ships.
- **Both services use `root: "."`.** The repo has one `package.json` (a standing rule), and the backend has none of its own. The docs only show services in separate folders, so this was proven with a local `vercel build --prod` before relying on it. The build also showed that Vercel's builder type-checks from the entry file. A global `.d.ts` that nothing imports is invisible to it, hence the `/// <reference>` to `types/express.d.ts` in `app.ts`.
- **Redis from the Vercel Marketplace (Upstash, free plan); MongoDB stays on Atlas.** The Socket.IO adapter needs real pub/sub over TCP, and presence and rate limits need ordinary commands. Official Redis was the first pick, but it had no free plan left on the team, so the user chose Upstash. It speaks the Redis protocol over TLS (`REDIS_URL`), and ioredis plus the adapter work unchanged. Eviction is off: presence, rate-limit and cache keys must leave only by TTL. Atlas has to allow `0.0.0.0/0`, because Vercel Functions have no fixed egress IPs (Static IPs is a paid add-on), so its password must be strong. It was rotated after the old one leaked.
- **Everything in one region, next to the database.** The Atlas cluster is a free M0 on GCP `asia-south1` (Mumbai). The first deploy put functions and Redis in `iad1`, which made every query a ~200 ms round trip across the world. Functions are pinned with top-level `"regions": ["bom1"]` (Hobby allows one region; the local build showed the key is valid alongside `services`), and Redis was recreated in `bom1`. Mongo, Redis, the functions and the expected users are now all in the same region.
- **On a serverless instance, start connecting before anything can trigger a connect.** In `vercel.ts`, building the server first let the Redis adapter's subscribe start a `lazyConnect` client on its own, so the explicit `connect()` was then rejected, on every cold start. `server.ts` and the tests always connected first, which is why only production showed it. The order is now the same everywhere.
- **Health reports readiness, not a snapshot.** A Vercel instance only gets CPU while a request is in flight, so a connect started at module load advances in bursts. `/api/health` read `readyState` without waiting and showed Mongo "disconnected" for ~25 s on cold instances, even though real routes worked (Mongoose buffers queries inside the request). It now waits up to 5 s for a connection that is still opening, as the Redis `PING` always did, so the first request to a fresh instance answers truthfully.
- **CLI deploys only, no GitHub connection.** Every file change in this repo is auto-committed and pushed. Git integration would start a build per commit and could exhaust the Hobby plan's daily deployment quota. The CLI is pinned to 65.12.1 via `npx`: the global 63.x predates Services, and 66.x was under two weeks old.
- **Later, at the user's request: auto-deploy from a `release` branch only.** The GitHub repo is now connected and the Production Branch is `release`. `vercel.json` sets `git.deploymentEnabled: {"**": false, "release": true}`. The patterns are minimatch, and a branch deploys if *any* matching rule is `true`, so only `release` deploys. This was chosen over an Ignored Build Step script, because Vercel counts those skipped builds against the deployment quota. The auto-commit pushes to `master` therefore cost nothing, and shipping is a deliberate `git push origin master:release`. This was verified with one empty commit: pushed to `master`, no deployment; pushed to `release`, a production deployment (`release @ 55b39e7`, Ready).
- **Secrets per environment, never shown.** Production and preview get their own freshly generated JWT secrets, stored as Vercel *Secrets* (write-only), so they are never readable by `env pull`. Production never shares a secret with local dev. `MONGO_URI` is the user's credential, so the user enters it.
- **Nginx: security headers yes, script CSP no.** Nginx repeats HSTS, `X-Frame-Options: DENY` / `frame-ancestors 'none'`, nosniff, Referrer-Policy and Permissions-Policy on every response, including pages that helmet (API only) never sees. A `script-src 'self'` CSP for the Next.js pages would break App Router hydration, which uses inline scripts. That needs per-request nonces from `proxy.ts`, left as follow-up work. The API keeps helmet's strict CSP.
- **Compose: one image, two commands; only Nginx is published.** The same build runs `next start` (web) and `node backend/dist/server.js` (api). Mongo and Redis exist only on the compose network. TLS certs live in `deploy/nginx/certs/` (gitignored; `make-dev-cert.sh` creates a self-signed localhost pair). These files were written without Docker available to run them, and are recorded as unverified.

## Post-MVP fixes

- **The task catch-up replaces the list instead of merging, but protects live events.** The merge never removed a task deleted while the tab was disconnected or away from the project. It could also bring back a task a live `task:deleted` had just removed, or overwrite a live edit with a stale copy, if the event beat the fetch's response. The catch-up now runs in two halves. `tasksSyncStarted` (dispatched as the fetch starts) begins recording the ids of every live upsert or removal. `tasksSynced` then replaces the store with the fetched list (it's the full set, not a page), except for the recorded ids, which keep their current live state, present or absent. An id-set rather than timestamps was used because a task's `updatedAt` can't tell a deletion apart, and the server clock isn't the client's. The server-rendered hydrate still merges: the catch-up right after the join reconciles it.
- **Node pinned to `24.x` in `engines`.** `>=20` let Vercel pick the newest major on its own, which it had warned it would do. 24 is the version dev, the Dockerfile and Vercel already run.

## Email system, part 1: mailer + password reset

The email system is built in three parts, each paused for review: password reset, then email verification, then workspace invites. Unverified accounts will only get a banner, never a lockout (user's choice).

- **Providers: Mailtrap's sandbox in dev, Brevo in production, one SMTP code path.** `utils/mailer.ts` uses nodemailer (10.4.0, pinned) with `SMTP_URL`, so changing provider is an env change, not a code change.
  - **Production went from Resend to Brevo.** Resend is the only email provider on the Vercel Marketplace, so it was the first pick, and the user accepted its terms. But its installer requires a domain you own ("you must own a domain to be able to send"), and FlowSync only has `flowsync-eight.vercel.app`. Brevo's free plan (300 emails/day) allows **single-sender verification**: one confirmed address, no domain, delivering to anyone. The user chose Brevo over buying a domain or using Gmail SMTP. `MAIL_FROM` must be that verified address. The Resend-only code path was removed.
  - Mailtrap (the user's suggestion) catches every email in a web inbox and delivers none. Dev can therefore use made-up addresses, which invites will need.
  - With no `SMTP_URL`, dev prints the email to the backend console. Production throws instead: an email carries a live token and must never land in logs.
  - Tests capture mail in `testOutbox`. The test setup blanks `SMTP_URL`, so `.env`'s real settings can never reach a test.
- **Link base URL from config, never from the request.** `appUrl` resolves in this order: `APP_URL`, then `CORS_ORIGIN` (dev), then Vercel's system variables (the production domain in production, the deployment's own URL in a preview). Building it from the `Host` header would allow host-header poisoning: a forged `Host` mails the victim a real token pointing at an attacker's site.
- **Token handling:**
  - 32 random bytes, base64url. Only the sha256 is stored, in an `AuthToken` collection (with a `purpose`, so email verification can reuse it).
  - A TTL index deletes expired tokens. Lookups still check `expiresAt`, because the TTL monitor runs about once a minute.
  - Redeeming a token is an atomic `findOneAndDelete`, so it's single-use even under a race.
  - A new request deletes the user's previous reset tokens.
  - The token goes in the URL **fragment** (`/reset-password#token=…`). Browsers never send a fragment to any server, so it stays out of Vercel's request logs, proxies and `Referer` headers.
  - The page strips the token from the address bar through the Next.js router (`router.replace(pathname)`) on the **first focus into the form**, not on mount. The browser check showed why:
    - The router rewrites the URL from its own state while it starts up. A hash stripped on mount came straight back, whether through `window.history.replaceState` or `router.replace`.
    - Once the page is interactive, the strip sticks and the form keeps its state.
    - After a successful reset, `router.replace("/login?reset=1")` replaces that history entry, so Back can't return to it.
  - The token is read in an effect that keeps any token an earlier run already took. React Strict Mode (dev) runs effects twice, and the second run used to overwrite the token with "none". The browser caught this, not the unit test: React only double-runs effects when `<StrictMode>` is outermost, as Next.js places it, and not when it's nested inside the store `<Provider>`. The regression test now renders it outermost.
- **Show/hide toggle on every password field** (user request): `components/auth/PasswordInput.tsx` is used by login, register and both reset fields. It's a real `type="button"`, so it never submits the form. Its `aria-label` says what it will do ("Show password" / "Hide password"), and `aria-pressed` gives its state.
- **A reset signs out every session.** It bumps `tokenVersion`, the hook `User` has carried since Step 3, so every refresh token dies. Access tokens are stateless and live out their ~15 min, and a connected socket stays up until it reconnects (the same accepted limit as logout, see Step 6). The reset doesn't log the user in: they log in with the new password, which proves they know it. The response clears this browser's cookies only when they belong to the reset account. The first version cleared them unconditionally, and the live check showed what that means: opening the link in a browser logged in as someone else logged *them* out.
- **Enumeration: same answer, 429 before lookup, timing not hidden.**
  - `forgot-password` always answers 200 with the same message.
  - The per-email limit (3/hour, Redis) runs before the account lookup, so a 429 reveals nothing either.
  - The extra time a real send takes isn't masked: registration's 409 already tells anyone whether an email is taken, so hiding it here would add complexity without closing anything.
  - A failed send is logged, not reported, so a 500 can't reveal existence either.
- **Mail errors are scrubbed before anything logs them, and `SMTP_URL` is checked before use.** On the first production deploy, `SMTP_URL` had been entered as the key followed by the URL. nodemailer's `TypeError` quoted the whole string, and `requestPasswordReset` logged it, so the Brevo key ended up in Vercel's runtime logs. The key was treated as leaked and rotated. Now:
  - `smtpUrlProblem()` rejects anything that isn't `smtp(s)://login:password@host`, with a message that never contains the value.
  - Errors from `createTransport` and `sendMail` are rethrown as fresh `Error`s, with the URL and the password (raw and URL-decoded) replaced by `<redacted>`.
  - A bad `SMTP_URL` doesn't crash the API (unlike the other env vars). Reset requests still answer normally, and the log says what's wrong.
- **No CSRF on these two routes.** No session is involved, and the reset token is itself the credential. A forged cross-site `forgot-password` can at most send the owner a reset email they didn't ask for, and the rate limit caps that.
- **Env changes need a redeploy on Vercel.** A deployment keeps the environment it was built with, so the rotated `SMTP_URL` only took effect after `vercel redeploy`. The key was entered through a hidden `read -s` prompt and the URL built around it, so the value was never echoed and couldn't be mis-ordered again.

## Email system, part 2: email verification

- **Banner, not lockout** (the user's choice in part 1). `User.emailVerifiedAt` is `null` until verified, and nothing on the API checks it. The app shows `EmailVerificationBanner` under the header with a **Resend email** button. Existing accounts start unverified and see the banner too. Nothing they did proved the address, and the banner only asks.
- **Same token machinery as reset, with the purpose enforced.** Verification tokens use the same rules as reset tokens: `AuthToken`, sha256 only, fragment link, atomic single-use redeem, a new one retires the old. The issue/redeem helpers are shared now. Every redeem filters on `purpose`, so a verification link can't reset a password and a reset link can't verify. A test covers both directions, and a mutation check confirmed it fails without the filter. The link lasts 24 h, not 30 min: it unlocks nothing, so it can be a lot more forgiving.
- **The page waits for a click.** `/verify-email` posts the token only when the user presses **Confirm my email**, not on load. Mail security scanners (Outlook Safe Links and similar) open links, and some run their scripts. With auto-verify, anyone who registered with someone else's address would get it "verified" by the victim's scanner. This matters more in part 3: invites are addressed to an email, so a verified address will mean something. It costs one click.
- **No login needed to verify.** The token is the credential, and people often open the email on their phone, where they aren't logged in. So `verify-email` has neither auth nor CSRF, like `reset-password`. The success screen links to `/dashboard`, which redirects to login if needed.
- **A password reset also verifies.** Clicking a reset link proves exactly what a verification link proves: the person controls the inbox. So the reset sets `emailVerifiedAt` if it was empty. That also clears the banner for anyone who has already reset their password.
- **Sending failures: silent at registration, reported on resend.** Registration logs a failed send and still creates the account, because the banner is the retry. Resend is a request for that email, so a failure there answers 503 "couldn't send", with the details only in the log. There's no enumeration concern: the user is logged in and it's their own address.
- **Resend limits:** 3 per user per hour (Redis), checked after "already verified" (400). Keying on the user id rather than the email is fine here, because the route needs a session.
